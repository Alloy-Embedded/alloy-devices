# Builders — regenerating chips/ from pinned sources (DRAFT)

This is the design for the pipelines that replace bootstrap-era hand mining. It
implements the exit criterion in [ARCHITECTURE.md](ARCHITECTURE.md): per family, a
builder regenerates every `chips/` file from pinned upstream sources, after which hand
edits to that family's chip files are rejected by CI.

Ground rule inherited from [NORTH_STAR.md](NORTH_STAR.md) and restated up front:
**builders generate ONLY chip instance files.** `registers/` is curated by humans,
forever. Builders *read* `registers/` (to validate IP references, gate register names
and clock-program fields) but never write a byte of it.

## Why this design is shaped the way it is

The previous ecosystem (`alloy-devices-yml`) died of unvalidated bulk data, and the
mechanism of death is instructive:

- It had **two trees**: `vendors/` (canonical, codegen-admitted) and `bulk-admitted/`
  (8,500+ auto-extracted YAMLs). The trees drifted immediately — `bulk-admitted/`
  carried a "symlink-ish copy" of the schema, its own report format, and its own
  quality bar (none). Promotion was a manual file *move* with no diffable review.
- Its sources were pinned to **dates, not SHAs** ("cached mirrors as of 2026-04-28"),
  so no run was reproducible.
- CI validated everything against a dead schema; everything passed by failing
  silently. "588 admitted devices, 3 working."

Every decision below is the inverse of one of those failures. The sharp line between
validated and generated data is kept — but it is drawn by **gates and provenance**,
not by directory boundaries, because directory boundaries are what failed.

## 1. Layout: one tree, `builders/` as input, `chips/` as output

```
builders/
  common/                shared library: fetch-by-SHA + cache, canonical YAML emitter,
                         diff/--check driver, ip-usage reporting
  st/
    build.py             entry point: `uv run alloy-devices build st [--check] [--only 'stm32g0*']`
    sources.lock         pinned upstreams: repo URL + git SHA + license note + role
    ip_map.yaml          upstream (kind, version) tag -> registers/st/<ip>  |  'uncurated'
    clock_templates/
      g0_boot.yaml       always-safe boot profile template (internal osc, no PLL)
      g0_pll.yaml        curated, hardware-verified PLL profile template (parameterized)
    patches/             overrides for upstream data errors, each with provenance
    verified.yaml        hardware-verification records to re-stamp into generated provenance
```

Build output goes **directly into `chips/st/`**. There is no `chips-generated/` tier
directory. Rationale:

1. **One consumption path.** The alloy codegen looks up `chips/<vendor>/<part>.yaml`
   and nothing else. A second tree forces every consumer to implement search order and
   merge logic — which is exactly where "best effort" parsing creeps back in, the
   thing the schema-pinning contract exists to forbid.
2. **The old failure was gates, not location.** `bulk-admitted/` was poison because it
   was admitted *below the validation floor*, not because of where it sat. Here the
   floor is uniform: **nothing enters `chips/` — hand-written or generated — without
   passing the same schema + plausibility lints.** A builder run that emits a file
   failing lints is a failed build, full stop. "Generated" is not a lower quality
   tier; it is a different *production method* recorded in provenance.
3. **Promotion is a diff, not a move.** When a family graduates, the builder's output
   replaces the hand-curated files in place; git history of each chip stays continuous
   and the graduation diff is reviewable line by line. In the old repo, promotion was
   an unreviewed `mv`.
4. **Hand-edit rejection needs no second tree.** CI runs `build --check` per graduated
   family (§5); any hand edit to a generated file drifts from the deterministic
   rebuild and fails CI. The directory boundary would add nothing the check does not
   already enforce.

What distinguishes a generated file (both auto-stamped by the emitter):

- a header comment: `# GENERATED by builders/st — do not edit. Regenerate: uv run
  alloy-devices build st. Sources: builders/st/sources.lock`
- `provenance.generator:` block: builder id, builder version, each upstream as
  `repo@sha (license)` copied from `sources.lock`. **No timestamps** — provenance
  identifies inputs, and timestamps would break determinism (§5).

`sources.lock` entry shape (illustrative):

```yaml
- name: stm32-data-generated
  repo: https://github.com/embassy-rs/stm32-data-generated
  sha: <40-hex git sha>
  license: "MIT OR Apache-2.0 (data derived from STM32_open_pin_data, BSD-3-Clause)"
  role: chip list, memories, peripheral bases/versions, IRQs, pin AF tables, DMA requests
```

EULA-gated feeds (NORTH_STAR guard 3) never appear in `sources.lock`; their extracted
facts enter via `patches/` with provenance, explicitly outside the reproducibility gate.

## 2. The ip_map contract: uncurated IPs

`builders/st/ip_map.yaml` maps the upstream's peripheral tag — for embassy stm32-data,
the `(kind, version)` pair of each peripheral's register block — to one of our curated
IP files, or to the literal `uncurated`:

```yaml
usart:v4:  st/usart_v4
gpio:v2:   st/gpio_v2
lptim:v1:  uncurated
```

An **unmapped** tag encountered during a build is an error — the map must be total
over the family being built, so new upstream tags are surfaced loudly instead of
silently dropped.

When a chip's peripheral maps to `uncurated`, the builder **emits the peripheral
without an IP binding**, marked explicitly:

```yaml
lptim1:
  uncurated: true
  ip_hint: "lptim:v1"        # the upstream tag, verbatim — the curation backlog signal
  base: '0x40007C00'
  gate: { peripheral: rcc, register: APBENR1, bit: 31 }
  irq: TIM6_DAC_LPTIM1
```

Why this and not the alternatives:

- **Omitting the peripheral** loses real facts we already validated the pipeline for:
  base, gate, IRQ, and — critically — pin routes and DMA request numbers that
  reference it. It also makes later curation of the IP a churny re-add instead of a
  one-line `ip_map.yaml` change plus regeneration.
- **Blocking the chip** kills coverage entirely: essentially every chip has *some*
  uncurated IP (RNG, CRC, CEC…). Nothing would ever generate, which is just the
  bootstrap stalemate with more steps.
- Emitting with a fake/guessed binding is the old repo's stub disease and is banned.

Schema change required (`alloy.chip.v1` → `v1.1`): a peripheral entry requires `base`
plus **exactly one of** `ip` or `uncurated: true`; `ip_hint` allowed only alongside
`uncurated`. Accompanying lint rules:

- A peripheral **referenced by** anything load-bearing — a `gate.peripheral`, a clock
  program op, a `companions` target — must be curated. (RCC/FLASH can never be
  uncurated on a shipped chip; this falls out naturally since clock programs
  reference them.)
- Routes and `dma_requests` **may** reference uncurated peripherals (the data is kept)
  — consumers must skip emitting API for them. The codegen contract: an uncurated
  peripheral produces *nothing* in generated C++ except its IRQ number in the vector
  table (which comes from `interrupts:` anyway).
- `alloy-devices report` prints the uncurated-IP histogram across `chips/` — "which
  register file, if curated next, unblocks the most peripherals" becomes a query, not
  a guess.

## 3. Clock strategy at scale

Two layers, both expanded by the builder into ordinary per-chip `clock.profiles.*`
programs — consumers never see templates, only expanded op lists that the existing
clock lints validate field-by-field against the curated RCC/FLASH register files.

**Layer 1 — generated boot profile, every chip, always.**
`builders/st/clock_templates/g0_boot.yaml`: internal oscillator, no PLL, correct
flash latency for the boot frequency. Parameterized by per-chip data (osc Hz from
upstream, latency from the family template's latency table). This is the always-safe
program: if it is wrong for any chip in the family, it is wrong for all of them, and
the fix is one template edit + regeneration.

**Layer 2 — curated PLL profile templates, family by family.**
`g0_pll.yaml`: a parameterized sequence (target sysclk → M/N/R fields, VCO range
check 64–344 MHz, latency thresholds) whose *ordering* encodes the hardware-found
knowledge — latency before switch, PLLREN before PLLON, poll PLLRDY, poll SWS. The G0
template's provenance cites the hardware-verified sequence (old-alloy `6d47f2cb` on
Nucleo-G071RB). A family without a curated PLL template still ships every chip — with
the boot profile only. That is a *visible* capability gap, not a blocker.

Templates live in `builders/st/clock_templates/`, not in `chips/` or a top-level
directory, because they are **build inputs** exactly like `ip_map.yaml`: hand-curated,
reviewed, never consumed downstream. The strong correctness check is not on the
template file — it is on every expansion, because expanded programs are linted against
the curated register files per chip (unknown field name, value exceeding field width,
implausible frequency all fail the build).

Each expanded profile records its origin: `template: st/g0_pll@<template git-tracked
version>` inside the chip's provenance.

## 4. What is NEVER generated

| Artifact | Why |
| --- | --- |
| `registers/*` | Curated per IP version by humans; the entire point of the model. Builders read, never write. |
| Boards (`board.json` in the alloy repo) | A board is a physical object with owner-verified wiring; one file per board, hand-curated, referencing chips by part id. |
| `schema/*`, lints, `NORTH_STAR.md` guards | Governance. Generated governance is no governance. |
| `builders/*/sources.lock`, `ip_map.yaml`, `clock_templates/`, `patches/`, `verified.yaml` | Builder *inputs* — hand-maintained, PR-reviewed. |
| Support tier claims (§6) | Tier-1 evidence rows are hand-entered with links to hardware logs; the matrix is *computed* from them, never hand-claimed. |

**Hardware knowledge survives regeneration** via two builder inputs:

- `builders/st/verified.yaml` — the hardware-verification records currently living in
  hand-curated `provenance.verified:` blocks (e.g. the G071 PLL field judgments, the
  GPIOC gate find). The builder re-stamps matching records into generated provenance,
  so regeneration never erases what hardware taught us.
- `builders/st/patches/` — when *upstream* data is wrong, the fix is a patch entry
  with provenance ("RM0444 §X says…, measured on hardware…"), applied during build.
  Hand-editing the generated chip file is never the fix (NORTH_STAR guard 5: fixes
  flow upstream — and a patch here should also be reported to the upstream project).

## 5. Incremental flow: deterministic diffs and `--check`

**One writer.** `builders/common/emit.py` is the only code that serializes chip YAML:
sorted keys wherever order is not semantic (peripheral dicts alphabetical, interrupts
by number, routes by `(pin, peripheral, signal)`), fixed dumper style matching the
existing files, quoted hex strings, LF, trailing newline, no timestamps. Result: a
rebuild from unchanged inputs is **byte-identical**, and a `sources.lock` bump
produces a git diff that expresses "what changed upstream" in our schema — reviewable
like any other data PR.

**Modes.**

- `alloy-devices build st` — fetch (cache-first), build, lint, write `chips/st/`.
- `alloy-devices build st --check` — build into a temp dir, diff against `chips/st/`,
  exit nonzero with a diff summary. Never writes.

**Fetching.** By pinned SHA into a gitignored cache (`.cache/sources/<name>/<sha>/`);
network touched only on cache miss; CI caches keyed by SHA. Raw upstream data is never
committed (NORTH_STAR guard 3).

**CI jobs** (extending the existing validate job):

1. `uv run alloy-devices validate` — schema + lints over everything (exists today).
2. `uv run alloy-devices build <family> --check` for every **graduated** family —
   fails if `chips/` drifted from what `sources.lock` + builder code + builder inputs
   produce. This single check catches all three drift modes: hand edits to generated
   files, builder changes without regenerated output, and lock bumps without applied
   output.
3. Determinism test: build twice, byte-compare (guards against nondeterministic
   iteration sneaking into a builder).

**Upgrade flow.** Bumping upstream = one PR containing the `sources.lock` SHA change
*and* the regenerated `chips/` files. CI proves they correspond; review reads the data
diff.

## 6. Support tiers

| Tier | Meaning | Evidence |
| --- | --- | --- |
| 1 `silicon` | A board in the alloy repo runs on this chip | board id + link to hardware log/commit |
| 2 `ci-compiled` | Alloy's CI compile matrix builds firmware for it | alloy repo CI matrix |
| 3 `generated` | In `chips/`, lint-clean, no compile/silicon evidence | — |

**Recorded where:** *not* in the chip file. A tier inside a generated file would
either go stale or force the builder to know about boards and CI runs — wrong
direction of dependency, and it is exactly the "hand-claimed support matrix"
NORTH_STAR bans. Instead:

- `support/<vendor>.yaml` in this repo holds **tier-1 rows only**, hand-curated, each
  with `part`, `board`, `evidence` (link to hardware log / framework commit), `date`.
- Tier 2 is **derived**: the alloy repo's CI publishes its compile-matrix result as a
  machine-readable artifact; the publish step here consumes it.
- Tier 3 is the default for everything else in `chips/`.

**Surfaced how:** the publish step computes `support_matrix.json` into the released
artifact. `alloy boards` / `alloy chips` print the badge (`silicon-validated`,
`builds-in-CI`, `generated-untested`), and the docs support-matrix page is generated
from the same JSON. Nobody types a support table by hand, ever.

## 7. Graduation: what "reproduce the hand files" means operationally

ARCHITECTURE.md says "byte-identically". The operational form, per family:

1. **Fact-identical gate.** `alloy-devices compare-graduation <family>` asserts every
   hand-curated *fact* (bases, gates + styles, IRQ names/numbers, memory sizes, routes,
   DMA requests, channels, clock programs op-for-op) is reproduced exactly. Provenance
   *narratives* are exempt — they are replaced by the generator stamp plus re-stamped
   `verified.yaml` records (§4), which is how byte-identity is reached in practice.
2. Every divergence is **judged, in the commit message**: upstream wrong → `patches/`
   entry with provenance; our hand file wrong → acknowledged fix. Silent adoption of
   either side is not an option.
3. **Hardware re-check** where a board exists: the family's tier-1 chip(s) re-run
   their board bring-up from the regenerated file before the family is marked
   graduated.
4. Graduation is recorded in `builders/<vendor>/build.py` (list of graduated families)
   which is what enables the `--check` CI job — from that commit on, hand edits to
   those chip files fail CI.

## 8. Pilot: STM32G0 via embassy stm32-data (~60 parts)

**Source:** pin `embassy-rs/stm32-data-generated` (MIT OR Apache-2.0; data derived
from ST's BSD-3 STM32_open_pin_data + Cube database) — consuming the generated JSON
avoids running embassy's extraction pipeline while staying pinned to one SHA. One
chip JSON per part number (STM32G030C6 … STM32G0C1VE) carrying cores, memories,
peripherals with `(kind, version)` register tags, IRQs, pin AF tables, DMA requests.

**Expected ip_map (to be confirmed by the dump step — step 2 below — not asserted
from memory; embassy's version tags do not always match our IP names):**

| upstream tag (expected) | ours |
| --- | --- |
| `gpio:v2` | `st/gpio_v2` |
| `usart:v4` | `st/usart_v4` |
| `spi:v2` | `st/spi_v2` |
| `i2c:v2` | `st/i2c_v2` |
| `adc:<g0 tag>` | `st/adc_v2` |
| `timer:<gp16 blocks>` (TIM2/3/14/15/16/17) | `st/tim_gp16` |
| `dma:<g0 tag>` | `st/dma_v1` |
| `dmamux:v1` | `st/dmamux_v1` |
| `rcc:g0` | `st/rcc_g0` |
| `flash:g0` | `st/flash_g0` |

**Expected uncurated on G0** (the honest gap list, becomes `ip_hint` stubs):
`lptim`, `ucpd`, `rng`, `crc`, `dac`, `cec`, `comp`, `vrefbuf`, `exti`, `syscfg`,
`pwr`, `iwdg`, `wwdg`, `rtc`, `tamp`, `dbgmcu`, advanced timer `tim1`, basic timers
`tim6/7`, `lpuart` (if tagged distinctly from usart), and on G0B1/G0C1 additionally
`usb`, `fdcan`, `crs`, `aes`. Roughly 15–20 uncurated kinds — the report histogram
from step 5 sets the curation order for new `registers/st/` files.

**Known policy decisions the pilot must land:**

- *File naming:* one file per stm32-data part number, lowercase (`stm32g030c6.yaml`).
  The existing `stm32g0b1.yaml` (part STM32G0B1RE) gets renamed to its part number on
  graduation.
- *Packages:* stm32-data carries per-package pinouts per part; emit the pin set for
  the part's package(s) (union where a part number spans packages), noted in
  provenance. A future `package:` field can narrow; boards pin exact parts anyway.
- *Route volume:* full AF tables mean hundreds of routes per chip (vs ~8 hand-mined).
  This is desired — bulk 1.3.0's AF tables were the one thing the old repo got right —
  but lints must stay fast at that volume.

Step 4 is the load-bearing one: it is the first time the "builders reproduce the
hand-curated bootstrap" promise is tested against files that found five real bugs by
hand. Divergences there are not noise — each one is either an upstream bug we must
patch with provenance, or a hand-mining error we must own. Both outcomes make the
database better; ignoring either is how the last repo died.
